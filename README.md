### 02 / Looking at my work through a security lens

**From features to security questions**  
A learning note based on my contribution to a team university application.

Building account flows, persistence, and admin features gives me a concrete place to start asking:

- What should the application trust?
- Who should be allowed to change a record?
- What happens when saving fails?
- What would need to change before real people could rely on it?

The note connects implementation choices with their limits and possible next steps.

### 03 / The way I work

**Follow the data.** Understand where it comes from, how it changes, and where it ends up.

**Check the unhappy path.** A failed operation should produce a clear error, not a misleading success message.

**Make the reasoning visible.** Write down assumptions and interfaces so other people can build on the work.
